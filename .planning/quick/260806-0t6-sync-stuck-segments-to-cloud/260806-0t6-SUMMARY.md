# Quick Task 260806-0t6: Sync stuck segments to the cloud

One-liner: `trip_stuck_segments` was device-only, so a reinstall restored a
trip's aggregate `timeStuckSeconds` but silently dropped every painted slow
stretch on its map; segments now travel with the trip document in both
directions.

## The gap

`TripDoc` carried `breaks` but had no stuck-segment field. Confirmed on device
during the pre-release smoke test: two trips restored from the cloud with
1880 s and 3501 s of stuck time and **zero** segment rows. The trip detail
screen degraded cleanly (no crash) and the moving/stuck bar stayed correct —
only the map overlay, the feature built for this release, disappeared.

## Approach

Mirrored the Phase 26 breaks implementation end to end rather than inventing a
second mechanism, because breaks are the exact structural analog: embedded
child rows synced with their parent trip.

**Backend** — `StuckSegment` type + `Trip.stuckSegments`; `stuckSegmentSchema`
with `kMaxStuckSegmentsPerTrip = 200` and `.default([])`; converter defaults
the field per-document for pre-existing docs; both handlers project it.

**Client** — `segmentsForTrip` / `segmentsForTripIds` (batched, no N+1 during a
drain) and `deleteSegmentsForTrip` on the DAO; `ParsedTrip` carries segments;
`toJson` truncates to the cap for the same poison-pill reason as breaks;
`fromJson` assigns fresh UUIDs but preserves the ORIGINAL point indices;
restore inserts them in the same per-trip transaction as breaks; enrichment
adopts cloud segments when local has none.

### The one place breaks were NOT copied

A break is defined purely by timestamps, so it is valid against any trip whose
window contains it. A stuck segment additionally carries
`startPointIndex`/`endPointIndex` into the DECODED `routePolyline` — and the
merged trip always takes **cloud's** polyline, because `routePolyline` is not a
selectable field and `merged` is built with `cloud.copyWith(...)`. Returning
local segments computed against a different polyline would paint the wrong
stretch of road as slow, which is a visible lie about the one thing this app
measures. Hence: cloud segments win when present; local ones only when the
polylines are identical (the common case, and the one that matters right after
this shipped); otherwise none.

The same reasoning surfaced a **latent pre-existing bug** in the conflict
sheet's "Use Cloud" branch, which replaced the trip's polyline while leaving
the local segments in place — their indices already addressed the old
geometry. Now fixed.

## Compatibility

Additive and safe in both directions: documents written before the field omit
the key and read as `[]`; clients older than this release keep omitting it and
still validate.

## Deviation from the approved plan

The plan routed this through `/gsd-plan-phase` as a full phase. It was executed
inline instead, with this quick-task record standing in for the phase
artifacts. The work itself matches the plan; what was skipped is the
planner/checker/verifier agent cycle.
